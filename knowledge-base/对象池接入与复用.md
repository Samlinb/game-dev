# 对象池接入与复用（Cocos Creator 3.x）

适用：Cocos Creator 3.6–3.8（按 v3.6.0 / v3.8.0 引擎源码核对），TypeScript；子弹、飘字、消除方块这类**高频创建销毁**的节点。低频对象直接 `instantiate`，别为池化而池化。核对日期：2026-11-11。

## 结论（影响行动的部分）

- **引擎自带 `NodePool`，不用自研**：`import { NodePool } from 'cc'` 即可。3.8 中它实现在内置扩展 `extensions/ccpool/node-pool.ts`，由 `exports/base.ts` 统一从 cc 模块导出（[源码](https://github.com/cocos/cocos-engine/blob/v3.8.0/extensions/ccpool/node-pool.ts) · [导出位置](https://github.com/cocos/cocos-engine/blob/v3.8.0/exports/base.ts#L55)，核对 2026-11-11）。3.8 手册没有专门的对象池页面，API 行为以引擎源码为准；2.4 手册的[对象池页面](https://docs.cocos.com/creator/2.4/manual/zh/scripting/pooling.html)概念仍适用但 API 细节不同。
- **一个 prefab 一个池**。池按「节点种类」建实例，不是全局一个池装所有节点（源码类注释明确）。
- **`put` 只摘节点、不清理**：自动 `removeFromParent()`，但源码注释写明 "without cleanup"——计时器、Tween、事件监听都不会被池停掉，清理责任在对象自己（见下节）。
- **`get` 池空返回 `null`，且不挂父节点**：取出后要自己 `addChild`；池空时的兜底（新建 or 放弃）由调用方决定。

## 最小流程：获取 → 初始化 → 归还 → 再次获取

```typescript
import { _decorator, Component, Node, Prefab, NodePool, instantiate, Tween, director } from 'cc';
const { ccclass, property } = _decorator;

// 1) 池处理组件：挂在 prefab 根节点上，负责自己的回收/复用逻辑
@ccclass('BulletHandler')
export class BulletHandler extends Component {
    unuse () {                 // 归还时：停动画/计时器、退订事件、清外部引用
        Tween.stopAllByTarget(this.node);
        this.unscheduleAllCallbacks();
        // this.node.off(...) / 全局事件退订写在这里
    }
    reuse () {                 // 再次取出时：完整重置全部状态（残留数据可能"几乎正确"，最阴险）
        this.node.setPosition(0, 0, 0);
        this.node.angle = 0;
        // 血量、速度、目标引用……全部字段显式初始化
    }
}

// 2) 使用方：建池、取、还
@ccclass('BulletSpawner')
export class BulletSpawner extends Component {
    @property(Prefab) template: Prefab = null;
    private pool = new NodePool('BulletHandler');   // 传组件类名字符串或构造函数均可

    fire (pos: Vec3) {
        let bullet = this.pool.get();               // 池空返回 null
        if (!bullet) bullet = instantiate(this.template);
        bullet.setParent(this.node);                // get 不会自动挂父节点
        bullet.setPosition(pos);
        // ……发射逻辑
    }

    recycle (bullet: Node) {
        this.pool.put(bullet);                      // 自动 removeFromParent + 调 unuse
    }

    onDestroy () {
        this.pool.clear();                          // 销毁池内所有缓存节点，防孤儿节点
    }
}
```

（示例代码，未在本工作区项目运行；本工作区项目为团结引擎，见文末跨引擎对照。）

API 行为逐条（[源码](https://github.com/cocos/cocos-engine/blob/v3.8.0/extensions/ccpool/node-pool.ts)，核对 2026-11-11）：

| API | 行为 |
| --- | --- |
| `new NodePool(poolHandlerComp?)` | 参数是含 `unuse`/`reuse` 方法的组件**构造函数或类名字符串**；不传则无回调 |
| `put(node)` | 自动 `removeFromParent()`（不 cleanup）→ 调 handler 的 `unuse()` → 入池；同一节点重复 put 会被忽略（内部查重） |
| `get(...args)` | 弹出**最后一个**节点（LIFO）→ 调 handler 的 `reuse(args)`（get 的入参原样转发）→ 返回；池空返回 `null` |
| `size()` | 当前可用（闲置）节点数 |
| `clear()` | `destroy()` 池内全部缓存节点并清空 |

## 状态、监听、计时器由哪一侧清理

**归对象自己，池只管存取。** 两侧依据：

1. **引擎侧事实**：`put` 的源码注释明确 "remove from parent, but don't cleanup"。节点摘离父节点后，组件上的 `schedule` 计时器、`Tween`、事件监听都还在，下次 `get` 出来会带着上一世的残留继续跑。池不知道对象订阅了什么，代清理必然漏。
2. **模式侧依据**：《游戏编程模式》对象池章指出，池绕过了内存分配器「新内存刷魔数」的保护网，复用对象所在内存带着上一世**几乎正确**的数据，漏初始化的 bug 极难发现；因此初始化必须覆盖全部字段，且对象停用时必须清掉对外部的引用，否则闲置对象会连带阻止 GC 回收被引用者。[Object Pool 章](https://gameprogrammingpatterns.com/object-pool.html)（核对 2026-11-11）

`unuse` 清理清单（实践建议，按项目实际订阅情况增删）：

- `Tween.stopAllByTarget(this.node)`（以及以子节点/组件为 target 的 Tween）
- `this.unscheduleAllCallbacks()`
- 全局事件总线、`input`、物理碰撞监听的退订
- 置空对外部对象的引用（目标、父容器缓存等）

`reuse` 初始化清单：位置/旋转/缩放、业务数值、可见性、组件开关——**全部字段**，不依赖「上次用完应该是干净的」。

## 怎样验证复用

1. **同一性**：`put` 后再 `get`，断言 `===` 同一节点实例（不是新建）。
2. **池计数**：`put` 前后 `pool.size()` +1 / -1；连续发射回收后 size 稳定在峰值附近，不再持续增长（持续增长说明有节点没归还，泄漏在使用侧）。
3. **状态污染测试**：取节点 → 故意改脏状态（改位置、挂计时器、订阅事件）→ `put` → `get` → 断言全部回到初始值、无多余计时器/监听。这是复用 bug 的头号来源，值得写成固定回归用例。
4. **性能对照**：同屏大量生成/销毁场景下，用 Profiler 对比池化前后的帧耗时与 GC 尖峰（真机测，Editor 数据不作数）。

## 边界与坑

- **池内节点游离在场景树外**。`put` 后节点无父节点，若池挂在场景组件上而切场景时没 `clear()`，这批节点成为孤儿——既不渲染也不释放。切场景内存排查见 [Cocos 场景切换后内存排查](./Cocos场景切换后内存排查.md)。池挂常驻管理器时则相反：不要在切场景时误清。
- **池容量要调**：太小频繁兜底新建，太大白占内存。《游戏编程模式》给出池满四策略：调大容量杜绝溢出（关键玩法对象）/ 直接不创建（粒子特效）/ 顶掉最旧的（声音）/ 扩容后考虑收缩。[同上](https://gameprogrammingpatterns.com/object-pool.html)
- **对象大小差异大时按尺寸拆多个池**，单池按最大对象预留会浪费（同上）。
- 有 GC 的平台池化收益主要在**分配频率与 GC 尖峰**，不是「省内存总量」——池本身常驻一批实例。

## 跨引擎对照（本工作区项目证据）

本工作区项目是团结引擎（Unity）双平台小游戏，模板已实现同构方案：[PrefabPool.cs](../projects/MiniGameTemplate/Assets/_Project/Scripts/Res/PrefabPool.cs) 的 `IPoolable` 契约（`OnSpawn` 初始化 / `OnDespawn` 退订、停协程、重置）与本文 `reuse`/`unuse` 一一对应，清理责任同样归对象自己；`ClearIdle` 对应 `clear()`，且特别处理了「闲置实例随场景销毁后的空引用」。设计逻辑见 [Unity 小游戏项目架构](<./Unity 小游戏项目架构.md>)「对象池的清理责任归谁」一节。原则跨引擎通用：**池只管存取，清理归对象**。
