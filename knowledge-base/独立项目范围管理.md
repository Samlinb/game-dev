# 独立项目范围管理（overscoping 识别与裁剪）

适用：独立开发者 / 小团队游戏项目立项与中期自查。本工作区项目为微信+抖音 IAA 小游戏（小体量、快迭代），外部来源的数值建议多来自 PC/Steam 独立游戏语境，套用前注意第六节的适用性边界。
触发：功能越加越多、项目迟迟不能发布、立项时拿不准做多大。
核对日期：2026-11-13（Positech 博客 + Superjump 杂志原文）。GameDeveloper 一文 403 待复核。

## 结论（影响行动的部分）

1. **每个系统必须能对着核心玩法循环说明存在理由，说不出就砍**——这是最可操作的裁剪判据。
2. **首作健康周期 12–18 个月（PC 独立游戏口径），超过 3 年即危险信号**；小游戏体量应远小于此，以「周~月」计。
3. **识别 overscoping 的核心信号：不断加内容并相信这让游戏更好**，以及「为了塞进别处看来的酷功能而推翻现有工作」。
4. **引擎/技术栈定了就别换**，冻结到发布后一年；反复换引擎的最坏结果是换出去又换回来。
5. **完成并发布本身是技能**：完美主义/追热点/恐惧导致的永不发布，比发布一个不完美的游戏损失更大。
6. **V1 应「完整但小」**：内容分「必须随本体发布」与「成功后再扩展」两堆，不要围绕假想的无限 DLC 收入做架构。

## 一、overscoping 识别信号（自查清单）

来源：[Superjump：50 种毁掉独立游戏的方式](https://www.superjumpmagazine.com/50-ways-to-ruin-your-indie-game-and-how-to-avoid-them)，核对 2026-11-13。外部经验（媒体总结，非实测数据）。

| # | 信号 | 原文编号 | 背后机制 |
|---|------|----------|----------|
| 1 | 不断往项目里加东西，并相信这是在提升质量 | #8 Overscoping | 超出设计者能力边界；可持续性 = 知道何时停止添加 |
| 2 | 首作规划过大，同时还在学工具和写代码 | #23 Overdesigning | 学习成本与开发成本叠加，周期失控 |
| 3 | 看到别的游戏有酷功能，推翻当前工作去塞进来 | #32 Keep Adding Systems | 功能没有对着核心循环论证，为加而加 |
| 4 | 无休止定义游戏，迟迟不动手做 | #9 预生产过长 | 有人几周想清楚，有人烧掉几年；想法会变（坏主意/太大/有更好主意）是正常的 |
| 5 | 边学边做导致膨胀，简单想法吞掉数周课程 | #10 无开发计划 | 早期用短开发周期学流程，而不是用大项目学 |
| 6 | 项目反复搁置，从未走完完整开发周期 | #33 永不完成本体 | 搁置真正坏掉的项目可以，搁置一切就是问题 |
| 7 | 众筹延伸目标实际上把项目变成另一个游戏 | #28 延伸目标过度承诺 | 新增范围超出筹到的钱 |
| 8 | 围绕「无限 DLC 收入」设计架构 | #48 发布后过度承诺 | 假想收入支撑不了实际开发成本 |

**对照信号（反方向失败）**：#24 Underdesigning——纯换皮别人的设计低价卖。自查问题：**「能否说清玩家为什么选你的游戏而不是替代品？」** 说不出 = 还没到可上架状态。范围管理不是越小越好，是「核心循环有差异化 + 其余极简」。

## 二、裁剪决策依据

来源：[Superjump](https://www.superjumpmagazine.com/50-ways-to-ruin-your-indie-game-and-how-to-avoid-them)，核对 2026-11-13。

### 2.1 砍/留判据（按优先级）

1. **核心循环锚定法**（#32）：先写清核心玩法循环（玩家每 30 秒~5 分钟在做什么、为什么爽）。每个系统/功能问一句「它为核心循环的哪一环服务？」答不出 → 砍。
2. **完整但小**（#48）：把内容分两堆——「必须随 V1 发布」（缺了游戏不成立）与「成功后再扩展」（锦上添花）。V1 只做第一堆。
3. **周期反推**（#23）：首作超过 3 年 = 太长（PC 口径）；健康周期 12–18 个月。用目标周期反推功能量：做不完的提前砍，而不是延期。
4. **简单循环打磨优先**（#32 引例）：Clover Pit、Buckshot Roulette 的成功路径是打磨一个简单循环，而不是先造最大版本。

### 2.2 裁剪时的心理陷阱

- 「加功能 = 提升质量」是错觉（#8）：质量来自核心循环的打磨深度，不是系统数量。
- 「沉没成本」：已写了一半的系统若答不出存在理由，照样砍（#32 的「推翻现有工作去加酷功能」是同一错误的另一面）。
- 「只许成功」：把单个项目当唯一机会（#49 Only one game idea）会放大每个功能的「不敢砍」。正确心态：一个项目 = 一次尝试，手里保留多个后续项目想法。

## 三、常见失败模式与预防（两位开发者经验）

### 3.1 Positech（Cliff Harris，20+ 年单人工作室，4 款七位数收入游戏）

来源：[Common mistakes by indie game developers](https://www.positech.co.uk/cliffsblog/2021/10/14/common-mistakes-by-indie-game-developers)，核对 2026-11-13。外部经验（个人经验总结，PC/Steam 语境）。

| 失败模式 | 他的建议 | 适用性 |
|----------|----------|--------|
| 换引擎/工具/语言 | 冻结一切到发布后一年；他 20 年用 C++/VS2013/自研引擎/Excel2010；「生产力提升宣称都是扯淡」 | **通用**（本工作区规则「引擎选型定了就别换」同源） |
| 做自己不热爱的品类 | 浅调研替代不了深度熟悉；进陌生品类先预算 6 个月 + 500–1000 小时玩该品类头部作品 | 通用 |
| 营销太晚太少 | 有可见东西（哪怕是占位色块）就开始；每周最低限度持续输出；发布前应有几十篇内容 | 语境受限（见第六节） |
| 无营销预算 | 最低 $10k，理想为开发支出的 20–50%；他每款约 $100k | **PC/Steam 买断制口径**，小游戏 IAA 不适用 |
| 发布即弃养 | 玩家期待至少 12 个月更新；每周修复首周抱怨；买家是免费 QA | 部分通用（小游戏也需持续运营，但节奏不同） |
| 平台选错 | 他选 PC：移动端被大厂 F2P 统治、无七位数广告预算看不见 | **与本项目方向冲突**，见第六节 |
| 品类拥挤 | 立项前按日期排序看新品发布流，避开饱和品类 | 通用方法（小游戏应按平台榜单/买量素材密度做同类检查） |
| 不咨询有经验开发者 | 真正竞品是 COD/Fortnite/Netflix/Twitter，不是其他独立游戏；找有已验证成绩的人 | 通用 |

### 3.2 Superjump 补充的项目管理失败模式

来源：[Superjump](https://www.superjumpmagazine.com/50-ways-to-ruin-your-indie-game-and-how-to-avoid-them)，核对 2026-11-13。

| 失败模式 | 预防 |
|----------|------|
| 无预算跟踪（#25） | 首作别辞职；兼职收入养开发，避免财务压力与创作压力叠加 |
| 团队无分工（#31） | 2 人到几十人都要明确谁做什么；单人可暂时忽略，扩张时必补课 |
| 反复换引擎（#35） | 先调研再选；最坏结果是换出去又换回来 |
| 永不发布（#50） | 完美主义/追热点/恐惧都会阻塞发布；itch.io 连商店页成本都没有；完成和发布是让后续项目更容易的技能 |
| 众筹过早/期望过高（#26/#27） | 最低门槛 = 核心循环好玩的 demo；别把项目全押在众筹上；备选：缩范围/带更完整版本再发起/转发行商 |

## 四、立项自查清单（综合两来源）

立项或中期自查时逐条过：

- [ ] 能用一句话说清核心玩法循环，以及「玩家为什么选我不选替代品」（#24/#32）
- [ ] 每个已规划系统都能回答「为核心循环哪一环服务」（#32）
- [ ] 目标周期明确：首作 ≤12–18 个月（PC 口径；小游戏按周~月定）（#23）
- [ ] 内容已分「V1 必须」与「成功后扩展」两堆（#48）
- [ ] 品类做过拥挤度检查（按发布流/榜单）（Positech #2）
- [ ] 品类是自己深度熟悉的，或已预算补课时间（Positech #3）
- [ ] 引擎/技术栈已冻结，无「换个更好的」念头（Positech #4 / #35）
- [ ] 有预算跟踪，首作不辞职（#25）
- [ ] 手里有 ≥2 个后续项目想法，本项目不是唯一赌注（#49）
- [ ] 有明确的发布目标和日期，而非「做完再说」（#50）

## 五、对本项目（微信/抖音 IAA 小游戏）的应用

以下为**本条目基于来源原则的推论**（非来源原文，小游戏语境）：

- 核心循环锚定尤其重要：IAA 休闲游戏的留存靠「30 秒上手 + 单局爽点」，任何不服务这一点的系统（复杂成长线、社交、多玩法模式）都是首选裁剪对象。
- 周期口径换算：PC 首作 12–18 个月 → 小游戏首作应以「数周出可玩版本、1–3 个月上线」为目标；超 3 个月仍无可玩版本即触发范围自查。
- 广告位/免广告设计（见 [小游戏免广告方案与IAA变现优化](./小游戏免广告方案与IAA变现优化.md)）属于核心循环的一部分（变现循环），不在「可砍系统」之列，但点位数量同样适用「每个点位说明存在理由」判据。
- 「发布即弃养」的反面同样适用：小游戏上线后按数据迭代（留存/广告渗透），但迭代方向由数据决定，不是预先堆功能。

## 六、适用性边界（来源冲突核对）

按任务书「来源冲突先核对是否描述不同平台/条件」：

| 来源建议 | 原语境 | 本项目语境 | 处理 |
|----------|--------|-----------|------|
| Positech「避开移动端选 PC」 | PC/Steam 买断制，无买量预算则移动端不可见 | 微信/抖音小游戏 = 平台内分发 + IAA 买量生态，非 App 手游买断/内购红海 | **不采纳其平台结论**；其「无预算则 discoverability 差」的机制在小游戏买量语境下仍需正视 |
| Positech「营销预算 $10k 起」 | Steam 独立游戏自费营销 | 小游戏 IAA 靠平台流量 + 买量 ROI 模型 | 数值不通用；「营销是技术活不是可选项」的原则通用 |
| Superjump「12–18 个月健康周期」 | PC/主机独立游戏 | 小游戏体量小得多 | 原则通用（周期反推功能量），数值按第五节换算 |
| 「引擎冻结」「核心循环锚定」「完整但小」「完成即技能」 | 通用 | 通用 | 直接采纳 |
